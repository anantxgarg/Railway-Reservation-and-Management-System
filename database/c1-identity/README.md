## Setup

```bash
createdb railway
psql -d railway -v ON_ERROR_STOP=1 -f schema.sql
psql -d railway -v ON_ERROR_STOP=1 -f schema_auth_tokens.sql   # only if the team approves it
psql -d railway -v ON_ERROR_STOP=1 -f seed.sql
psql -d railway -v ON_ERROR_STOP=1 -f seed_dev_users.sql       # development only
mongosh "mongodb://localhost:27017/railway" mongo/audit_log.js
```

Run the tests (builds and drops its own `railway_c1_test` database; needs `pip install bcrypt`):

```bash
PGHOST=localhost PGUSER=postgres ./tests/run_tests.sh
```

> `schema.sql` drops and recreates the C1 tables. Other teams' tables that reference `users` (e.g. `booking.user_id`) lose that foreign key when it runs, so in a shared database run C1 first, then the other modules' scripts.

## Contract for Member 1 (backend)

1. **IDs are `INTEGER`** (`user_id`, `role_id`, …), generated by the database. Never insert an ID yourself — the DB refuses it.
2. **E-mail**: always `lower(trim(email))` before INSERT *and* before the login lookup. The database rejects any e-mail that isn't already lower-case and trimmed; this is what makes uniqueness case-insensitive.
3. **Passwords**: store bcrypt only (`$2a$/$2b$/$2y$`, 60 chars). Anything else — including a plaintext password — is rejected by a CHECK constraint. Seed hashes use cost 12.
4. **Public registration**: insert with the `CUSTOMER` role_id; omit `status`, `failed_login_attempts` and timestamps — the defaults are `ACTIVE`, `0` and `now()`.
5. **Login may succeed only when `status = 'ACTIVE'`**. `INACTIVE`, `PENDING`, `SUSPENDED` and `LOCKED` must all be refused. The lockout threshold (how many failures before `LOCKED`) is Member 1's policy; the DB only stores the counter.
6. **Permission check** — one query:
   ```sql
   SELECT 1 FROM user_permissions
   WHERE user_id = $1 AND permission_name = $2 AND status = 'ACTIVE';
   ```
7. **Creating staff**: call `SELECT * FROM create_staff_user(name, email, phone, password_hash, department, location);` — never insert into `users` and `staff` separately. It returns `(user_id, staff_id)` and creates both or neither. Read the new rows in a *later* statement; a join in the same statement can't see them.
8. **Tokens** (if approved): store `encode(sha256(raw_token), 'hex')`, never the raw token; the DB rejects anything that isn't 64 hex chars.
9. **Audit log** (MongoDB): `user_id` is a **string** (`"5"`, not `5`), `timestamp` a BSON date, `result` `SUCCESS`/`FAILURE`, action/resource_type `UPPER_SNAKE_CASE`. Unknown fields are rejected, so a stray `password` field can't be written.

## Contract for Member 3 (frontend)

- Roles: `CUSTOMER`, `STAFF`, `ADMIN`.
- Account statuses to message: `ACTIVE`, `INACTIVE`, `PENDING`, `SUSPENDED`, `LOCKED`.
- Permission names: see the matrix below.
- Profile fields available: `user_id, name, email, phone, status, role_name, created_at, last_login_at`; for staff also `department, location`. Never expose `password_hash` or `failed_login_attempts`.

## Open decisions — need the team

1. **Permission matrix** — confirm with the C2/C4/C5 teams. Staff currently have only `VIEW_PASSENGER`; if staff should cancel bookings, mark train runs or similar, those permissions don't exist yet.
2. **Token tables** — `refresh_tokens` and `password_reset_tokens` are not in the 22-entity master schema. Either approve and add them to the DBML, or Member 1 drops refresh/forgot-password.
3. **Default status `ACTIVE`** — the enum has `PENDING`, which suggests e-mail verification. If verification is required, the default should be `PENDING`.
4. **Temporary lockout** — the schema has no "locked until" column, so lockouts are permanent until an admin resets them. Time-based lockout needs a new column.
5. **`staff.location`** — free text per the master schema. It could reference `station.station_code` (C2) to prevent typos.
6. **Audit log location** — the team plan put `audit_log` in SQL, but `schema_mongodb.dbml` puts it in MongoDB. This build follows the DBML. Member 1 therefore needs a MongoDB connection.
